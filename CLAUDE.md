## Design philosophy

- **I/O isolation.** Only `ingestion/pipeline.py` does network and pool I/O (and `calibration/referee_job.run_referee_job` for its own job, and `alerts/telegram.py` for Telegram calls and its sent-alert, message-index and alert-delivery state files, and `alerts/delivery.py` for the operator's delivery review (the delivery and message-index files, and Telegram for a re-send), and `alerts/ledger.py` for reading bet-recording replies (getUpdates, only from TELEGRAM_CHAT_ID) and its placed-bet and offset files, and its one read-only settlement query, and `alerts/predictions.py` for the prediction log file (and the pricing source files it fingerprints), and `alerts/lineup_capture.py` for one Sportmonks listing per run (through `VendorClient`) and its team-sheet files, and `alerts/status.py` for its read-only status query, and `alerts/scan.py` for the opportunity scan's read-only database query; its one Sportmonks listing call goes through `VendorClient`, and `ingestion/results.py` for the results job's listing call (through `VendorClient`) and read-only query, its writes going through `ConcurrentIngestionEngine`, and `alerts/fx.py` for its one exchange-rate request and rate cache file, and `alerts/task_health.py` for its state file and Telegram failure alerts). `scanner/slate.py`, `alerts/replies.py` (reply parsing and grading) and `evaluation/gate2.py` are pure. `config.py` reads `.env`. Vendor adapters such as `ingestion/sportmonks.py` are pure: response in, transform payload out. Workers fetch and parse first, then take a pooled connection for one short transaction inside `ConcurrentIngestionEngine._with_transaction`, which is the only `pool.getconn()` call site. Never pass connections, cursors, pools or sessions into `transform.py`, `engine.py`, `market_scanner.py`, `fitting.py` or `backtest.py`.
- **Mathematical conservatism.** The allocator maximises \(f^\top\mu - \lambda f^\top\Sigma f\) jointly over every line, book and player in a fixture, using the exact covariance from `fixture_moments` (shared game-state factor), with caps net of open exposure (`ExposureBook`) and the model-risk loss floor (`MODEL_RISK_LOSS_FLOOR` = 0.03, un-backtested). Never revert to nominal-EV selection or per-line sizing. Don't change risk defaults (`risk_aversion=2.0`, the caps, `alpha_threshold`, `MODEL_RISK_LOSS_FLOOR`) without an explicit human instruction.
- **Fail closed.** Raise `ValueError` or `ProjectionError` at the point of detection. Catch only at the sanctioned handlers in AGENT.md §1.3, each of which records the failure. No fallback distributions, no silent floors. The one clamp (relative variance up to its 1e-6 minimum) logs `[MATH_CLAMP]`; a relative variance above 1e3 raises.
- **Type rigidity.** Follow these rules; they are enforced by `tests/test_typing_contract.py`:
  - `from __future__ import annotations` in every module;
  - every parameter and return annotated;
  - `Sequence`/`Mapping` for read-only inputs;
  - `Final[...]` on module constants;
  - frozen dataclasses that validate in `__post_init__` for value objects.

**Opportunity scan** (`alerts/scan.py`, `scanner/slate.py`). Each run covers League One and Two fixtures kicking off in [now, next 4-hour boundary), so every fixture is scanned once, in its last 4 hours. It lists them with one Sportmonks call; prices every regular starter (≥ 40% of the team's last 5 starts) for tackles and fouls from their own last 20 appearances, with a trailing positional league level (`modeling/league_level.py`: this season's rate to date, shrunk towards last season's with 30,000 pseudo-minutes (tuned 2026-10-04); each past match's minutes weighted by its season's level over today's (passed to the engine as `exposure_scale`, so the minutes themselves stay within 130; until 2026-10-04 the scaled minutes could exceed 130 and refuse a whole fixture), so league-wide drift between seasons does not carry into prices; added 2026-10-04 after the quick backtest found tackles per 90 down 4% and fouls up 5% between seasons); then fetches odds, runs `allocate`, the high-value screen and `notify`. It sends at most `PROP_ALPHA_MAX_ALERTS` (default 10) bets, best expected profit first, as numbered digest messages of at most 5 bets each (`notify_digest`; each bet shows the match and kickoff, the player and club, the bet and odds, the minimum odds, the edge and the stake), then a one-message summary. Assumptions not yet fitted: lineups are estimated, not confirmed team sheets; the referee is neutral; `game_state_k` is 6.0 for tackles and 1000 for fouls (`SCAN_GAME_STATE_K_BY_MARKET`: the 2026-10-04 backtest found no game-state overdispersion in fouls); the tackles rate is multiplied by 0.9483 (`SCAN_RATE_MULTIPLIER_BY_MARKET`, level recalibration fitted by `scripts/recalibrate.py` on 2026-01-01 to 2026-09-12; fouls stay at 1 because their fitted multiplier made the selection window worse); card markets are not scanned. A fixture listing longer than 5 pages refuses the scan rather than scan part of the window. **Odds: `--odds oddspapi`** (the scheduled task) fetches real prices only when the window has fixtures: it reads the unmetered account endpoint first and skips odds if fewer than 20 of the free plan's 250 requests would remain, then makes one call per bookmaker in `ODDS_BOOKMAKERS` (default bet365, skybet, williamhill; only OddsPapi's HTTP 400 "does not have any fixtures available" reply is noted as "no fixtures"; any other 400 or 404 is an odds failure). A malformed reply from one bookmaker is that bookmaker's failure only (handler H12): its prices are left out whole, the summary says "Odds FAILED from <book>", and the raw body is archived as `<stamp>_<book>.rejected.json.gz`. Any other OddsPapi failure (403, 401, outage, request cap, a malformed account or catalogue reply) puts "Odds unavailable this run, nothing priced: …" in the summary and the run still completes (handler H11). **Fair-price boards are OFF (maintainer decision 2026-10-10: nothing below the high-value benchmark is sent; `scan.SEND_FAIR_BOARDS = False`):** a match where no bookmaker quote matched any player used to get a board instead; the scan summary now says how many priced matches had no bookmaker quote and nothing else goes to Telegram for them. The board mechanism below is kept and tested but not used. A board, when on, was sent once per match (`.prop_alpha_state/fair_boards_sent.json`): for each priced player and market, the line in `FAIR_LINES` closest to even, with each side's minimum odds (`slate.fair_price_board`: expected profit 4% after the 0.03 loss floor, as the high-value screen requires; void if the player does not play). Sides whose minimum odds fall outside `FAIR_MIN_ODDS_RANGE` (1.40–3.50) are left off. The maintainer compares these with any bookmaker by hand; boards carry the PAPER label and say stakes are token-only until the model is validated. Fixtures are matched by kickoff (±15 min) and club-name words, players by normalised name (or unique surname plus initial); anything ambiguous is left out and counted in the summary. Assumed until checked against settlement (step 3): OddsPapi tackles = Sportmonks `TACKLES`, fouls = `FOULS`, void if the player does not play, and a missing stake limit means GBP 50 (the alert says "book limit not published, assumed GBP 50"). ## Local PostgreSQL

Supported: **PostgreSQL 15 or newer** (the schema needs 15 for `UNIQUE NULLS NOT DISTINCT`; CI refuses older servers). Verified: **18.6**, installed natively on this machine with the EDB Windows installer:

- service `postgresql-x64-18`, port 5432, superuser `postgres`;
- binaries in `C:\Program Files\PostgreSQL\18\bin`, which the installer does **not** add to PATH. `ci/bootstrap.sh` finds the newest version there by itself; for manual use, call `psql` by full path or add that folder to PATH. A tool that reports "no psql" has usually only checked PATH;
- the password is in `%APPDATA%\postgresql\pgpass.conf` (outside the repo; `psql` reads it automatically). Never put it in a URL, file or command in the repo;
- CI database: `prop_alpha_ci`. CI stage 6 runs `DROP SCHEMA prop_alpha CASCADE`, so `ci/bootstrap.sh` resets a database only when three checks agree: it is named exactly `prop_alpha_ci` (`CI_DATABASE_NAME`), it carries the comment `CI_DATABASE_MARKER` (set on the local one on 2026-10-05: `COMMENT ON DATABASE prop_alpha_ci IS 'prop_alpha disposable CI database'`; never set it on a database you want to keep), and its `fixtures` and `player_match_stats` are empty.

Run the full pipeline, including the database stage (from Git Bash):

```bash
PROP_ALPHA_CI_DATABASE_URL="postgresql://postgres@localhost:5432/prop_alpha_ci" bash ci/bootstrap.sh
```

Stage 6 then: drops and reinstalls the schema from `schema.sql`; runs the merge on empty staging; runs `tests/test_merge_postgres.sql` (it rolls itself back); re-applies 005 to check it is idempotent; replays the upgrade path 003 → 004 → 005; and runs the merge test again. Without `PROP_ALPHA_CI_DATABASE_URL`, stage 6 is skipped and says so.

Manual checks (PowerShell):

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -w -h localhost -U postgres -d prop_alpha_ci -X -v ON_ERROR_STOP=1 -f schema.sql
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -w -h localhost -U postgres -d prop_alpha_ci -X -v ON_ERROR_STOP=1 -f tests/test_merge_postgres.sql
```

A **fresh database gets `schema.sql` only**, because it already includes every migration. Never apply `migrations/002_staging_and_indexes.sql` to a v3.2+ schema: it reinstalls the superseded v3.0 merge function and drops the minute-logic reject predicates. Migrations are for upgrading existing databases, in numeric order.

On a machine without a native install, Docker works too (untested here): `docker run --name prop_alpha_sandbox -e POSTGRES_DB=prop_alpha_ci -e POSTGRES_PASSWORD="$PGPASSWORD" -p 5432:5432 -d postgres:18-alpine`, with `PGPASSWORD` from `openssl rand -hex 16`, then the same CI command with `postgres:${PGPASSWORD}@` in the URL.

## Conventions

- **Naming.** `snake_case` for functions, parameters and columns (`padj_tackles`, `minutes_played`). `UPPER_CASE` with `Final[...]` for module constants (`MIN_RELATIVE_VARIANCE`, `MAX_MATCH_MINUTES`). Define each constant in exactly one module and import it; never redeclare.
- **Upsert ordering.** Two different orderings apply, and they must not be confused:
  - **Lock order:** every multi-row upsert orders by its conflict key, e.g. `ORDER BY f.fixture_id, p.player_id` for `player_match_stats`, so concurrent writers take row locks in the same order and cannot deadlock.
  - **Chronological order:** `DISTINCT ON (...) ORDER BY ..., staged_at DESC` only decides which staged version wins.

  Anything else that updates `referees` must take the merge's advisory lock (`referee_job.MERGE_LOCK_KEY`).
- **Numerics.** Vectorise with numpy when operating on data arrays: exposure vectors, outcome grids, estimator inputs. Plain Python `sum` is correct, and preferred, for exact integer tallies over dataclasses (`compute_referee_coefficients`) and for short fixed-size loops (log-sum-exp over a handful of terms). Never compute a variance as \(E[X^2]-\mu^2\) in `engine.py`: use the relative form \(1/\alpha + 1/k + 1/(\alpha k)\) (AGENT.md gate G1).
- **Database changes.**
  - Put every change in a new `migrations/NNN_*.sql`. Never edit an applied migration.
  - Mirror the change in `schema.sql`.
  - Add constraints `NOT VALID`, then `VALIDATE`; build indexes `CONCURRENTLY`; set `lock_timeout`.
  - Every new `CHECK` needs a matching Python validation and a merge reject predicate.
  - Never use `TRUNCATE` on staging.
- **Secrets.** None in code, tests or scripts. Tests need no credentials. The Telegram bot token and chat id live only in the gitignored `.env` (template: `.env.example`) or the process environment; `test_no_secrets_in_repository_files` scans for token-shaped strings.
