## Design philosophy

- **I/O isolation.** Only `ingestion/pipeline.py` does network and pool I/O (and `calibration/referee_job.run_referee_job` for its own job, and `alerts/telegram.py` for Telegram calls and its sent-alert, message-index and alert-delivery state files, and `alerts/delivery.py` for the operator's delivery review (the delivery and message-index files, and Telegram for a re-send), and `alerts/ledger.py` for reading bet-recording replies (getUpdates, only from TELEGRAM_CHAT_ID) and its placed-bet and offset files, and its one read-only settlement query, and `alerts/predictions.py` for the prediction log file (and the pricing source files it fingerprints), and `alerts/lineup_capture.py` for one Sportmonks listing per run (through `VendorClient`) and its team-sheet files, and `alerts/status.py` for its read-only status query, and `alerts/scan.py` for the opportunity scan's read-only database query; its one Sportmonks listing call goes through `VendorClient`, and `ingestion/results.py` for the results job's listing call (through `VendorClient`) and read-only query, its writes going through `ConcurrentIngestionEngine`, and `alerts/fx.py` for its one exchange-rate request and rate cache file, and `alerts/task_health.py` for its state file and Telegram failure alerts). `scanner/slate.py`, `alerts/replies.py` (reply parsing and grading) and `evaluation/gate2.py` are pure. `config.py` reads `.env`. Vendor adapters such as `ingestion/sportmonks.py` are pure: response in, transform payload out. Workers fetch and parse first, then take a pooled connection for one short transaction inside `ConcurrentIngestionEngine._with_transaction`, which is the only `pool.getconn()` call site. Never pass connections, cursors, pools or sessions into `transform.py`, `engine.py`, `market_scanner.py`, `fitting.py` or `backtest.py`.
- **Mathematical conservatism.** The allocator maximises \(f^\top\mu - \lambda f^\top\Sigma f\) jointly over every line, book and player in a fixture, using the exact covariance from `fixture_moments` (shared game-state factor), with caps net of open exposure (`ExposureBook`) and the model-risk loss floor (`MODEL_RISK_LOSS_FLOOR` = 0.03, un-backtested). Never revert to nominal-EV selection or per-line sizing. Don't change risk defaults (`risk_aversion=2.0`, the caps, `alpha_threshold`, `MODEL_RISK_LOSS_FLOOR`) without an explicit human instruction.
- **Fail closed.** Raise `ValueError` or `ProjectionError` at the point of detection. Catch only at the sanctioned handlers in AGENT.md §1.3, each of which records the failure. No fallback distributions, no silent floors. The one clamp (relative variance up to its 1e-6 minimum) logs `[MATH_CLAMP]`; a relative variance above 1e3 raises.
- **Type rigidity.** Follow these rules; they are enforced by `tests/test_typing_contract.py`:
  - `from __future__ import annotations` in every module;
  - every parameter and return annotated;
  - `Sequence`/`Mapping` for read-only inputs;
  - `Final[...]` on module constants;
  - frozen dataclasses that validate in `__post_init__` for value objects.

Every attempt, retries included, spends vendor quota. The client retries once by default, stops at `DATA_VENDOR_MAX_REQUESTS` per run, and stops for the run once the vendor reports `DATA_VENDOR_QUOTA_RESERVE` or fewer requests left (from a header, or Sportmonks' `rate_limit` body field). A 2xx reply with an `errors` body counts as a failure.

Telegram alerts (sends messages only; never places bets). Only high-value bets are sent (`scanner/value_screen.py`): mispriced by the book, at least 4% expected profit per unit staked, and an edge that still returns at least 4% in more than 60% of 1,000 simulated match conditions, all after the 0.03 model-risk loss floor. One alert per market, line, side and book. With a `SentAlertStore` (`.prop_alpha_state/sent_alerts.jsonl`, gitignored), that holds across runs, and `store.exposure(now)` must be passed to `allocate` so that a new run sizes net of earlier alerts. Every alert from the last 4 days counts as open exposure; a bet recorded as placed counts until it is settled or undone, however old. The `--demo` stays in memory. Each alert shows the minimum acceptable odds and an expiry. Every alert, digest and board message is also recorded in `.prop_alpha_state/alert_deliveries.jsonl` (`DeliveryLog`): pending before the send, delivered with Telegram's message id after it. A send that fails, times out or is cut off stays pending and is reported as "outcome unknown" (status report WARNING, `alerts.delivery`), because only the operator can see whether it reached the chat; nothing is re-sent automatically, and the alerted stake still counts as exposure. A reply to such a message proves it arrived: the poll matches the quoted text, records the bet and confirms the delivery. No message is ever truncated: a plain message over Telegram's 4,096 characters is split at line breaks, an alert or board message over it is refused before anything is recorded, and boards close a message before the limit. A board message already recorded is not sent again by a retried run. A sent message is indexed for replies before its delivery is confirmed, so a run stopped in between leaves it reviewable, never unanswerable. `ledger --poll` and `--settle` hold an OS lock (`.prop_alpha_state/ledger.lock`, released if the process dies), so a manual run during the scheduled one fails at once instead of recording a reply twice. `scan --at` (simulated run time) is refused with `--odds oddspapi`: it is for mock runs only:

**Opportunity scan** (`alerts/scan.py`, `scanner/slate.py`). Each run covers League One and Two fixtures kicking off in [now, next 4-hour boundary), so every fixture is scanned once, in its last 4 hours. It lists them with one Sportmonks call; prices every regular starter (≥ 40% of the team's last 5 starts) for tackles and fouls from their own last 20 appearances, with a trailing positional league level (`modeling/league_level.py`: this season's rate to date, shrunk towards last season's with 30,000 pseudo-minutes (tuned 2026-10-04); each past match's minutes weighted by its season's level over today's (passed to the engine as `exposure_scale`, so the minutes themselves stay within 130; until 2026-10-04 the scaled minutes could exceed 130 and refuse a whole fixture), so league-wide drift between seasons does not carry into prices; added 2026-10-04 after the quick backtest found tackles per 90 down 4% and fouls up 5% between seasons); then fetches odds, runs `allocate`, the high-value screen and `notify`. It sends at most `PROP_ALPHA_MAX_ALERTS` (default 10) bets, best expected profit first, as numbered digest messages of at most 5 bets each (`notify_digest`; each bet shows the match and kickoff, the player and club, the bet and odds, the minimum odds, the edge and the stake), then a one-message summary. Assumptions not yet fitted: lineups are estimated, not confirmed team sheets; the referee is neutral; `game_state_k` is 6.0 for tackles and 1000 for fouls (`SCAN_GAME_STATE_K_BY_MARKET`: the 2026-10-04 backtest found no game-state overdispersion in fouls); the tackles rate is multiplied by 0.9483 (`SCAN_RATE_MULTIPLIER_BY_MARKET`, level recalibration fitted by `scripts/recalibrate.py` on 2026-01-01 to 2026-09-12; fouls stay at 1 because their fitted multiplier made the selection window worse); card markets are not scanned. A fixture listing longer than 5 pages refuses the scan rather than scan part of the window. **Odds: `--odds oddspapi`** (the scheduled task) fetches real prices only when the window has fixtures: it reads the unmetered account endpoint first and skips odds if fewer than 20 of the free plan's 250 requests would remain, then makes one call per bookmaker in `ODDS_BOOKMAKERS` (default bet365, skybet, williamhill; only OddsPapi's HTTP 400 "does not have any fixtures available" reply is noted as "no fixtures"; any other 400 or 404 is an odds failure). A malformed reply from one bookmaker is that bookmaker's failure only (handler H12): its prices are left out whole, the summary says "Odds FAILED from <book>", and the raw body is archived as `<stamp>_<book>.rejected.json.gz`. Any other OddsPapi failure (403, 401, outage, request cap, a malformed account or catalogue reply) puts "Odds unavailable this run, nothing priced: …" in the summary and the run still completes (handler H11). **Fair-price board:** a match where no bookmaker quote matched any player (including every match when odds are unavailable) gets one board instead, sent once per match (`.prop_alpha_state/fair_boards_sent.json`): for each priced player and market, the line in `FAIR_LINES` closest to even, with each side's minimum odds (`slate.fair_price_board`: expected profit 4% after the 0.03 loss floor, as the high-value screen requires; void if the player does not play). Sides whose minimum odds fall outside `FAIR_MIN_ODDS_RANGE` (1.40–3.50) are left off. The maintainer compares these with any bookmaker by hand; boards carry the PAPER label and say stakes are token-only until the model is validated. The market catalogue (weekly) and team names are cached in `.prop_alpha_state/oddspapi/`; every raw response is archived in `.prop_alpha_state/odds_archive/` for closing-line analysis. Fixtures are matched by kickoff (±15 min) and club-name words, players by normalised name (or unique surname plus initial); anything ambiguous is left out and counted in the summary. Assumed until checked against settlement (step 3): OddsPapi tackles = Sportmonks `TACKLES`, fouls = `FOULS`, void if the player does not play, and a missing stake limit means GBP 50 (the alert says "book limit not published, assumed GBP 50"). Real alerts use the real alert store and carry no MOCK label. **`--odds mock`** (`slate.mock_quotes`: the model's own price plus logit noise, SD 0.2, and a 6% margin) is for testing: its alerts say MOCK on their first line and go to `.prop_alpha_state/mock_sent_alerts.jsonl`, never the real store. Bankroll: `PROP_ALPHA_BANKROLL` (default 1000) in `PROP_ALPHA_CURRENCY` (required; GBP or USD; the maintainer chose USD on 2026-10-04). Book limits are assumed to be GBP; with a USD bankroll the scan converts every limit at the ECB rate cached by `alerts/fx.py` (refreshed each 4-hourly run, refused when older than 5 days) and shows each stake in both currencies.

A Windows Task Scheduler task, `prop_alpha\Telegram status`, runs the results job, refreshes the exchange rate, then sends the status report and the opportunity scan every 4 hours (00:00, 04:00, …), running `scripts/telegram_status.cmd` with `.venv`, which CI never deletes. **Bet recording** (`alerts/ledger.py`, `alerts/replies.py`). Every bet is placed by hand. The maintainer records one by replying to the alert or board message it came from: `placed 3 @1.95 5` (bet 3 of that message, decimal odds, stake), `placed 2 under @2.10 10 skybet` (board rows list both sides, so the side is required; the book is optional), `undo 12`, `settled 12 lost`. A stake typed with `£` is converted to the bankroll currency at the cached rate (and kept as entered); no sign or `$` means the bankroll currency. Every sent digest and board message is indexed by Telegram message id (`.prop_alpha_state/alert_messages.jsonl`; mock runs use `mock_alert_messages.jsonl`, so a reply to a mock message is never recorded). Only TELEGRAM_CHAT_ID is read. Every answer is queued in `.prop_alpha_state/ledger_answers.jsonl` before the offset is saved and re-sent by the next poll (prefixed "Delayed answer") if its send failed, up to 3 tries; then the status report flags it. The BETS SETTLED message of `--settle --send` goes through the same queue (third delivery pass, 2026-10-05): settled bets are recorded first, so a failed send used to be lost for good; the next poll now re-sends it, prefixed "Delayed". An edited reply is answered with "Edits are not applied" and changes nothing. A placed reply identical to an open bet is recorded but flagged as a possible duplicate. Each poll records when it read Telegram (`ledger_last_poll.json`); the status report warns when that is over an hour old, and past 24 hours, when Telegram drops unread replies, says which replies to re-send. Bets go to `.prop_alpha_state/placed_bets.jsonl` with the Telegram update id, so a re-delivered update is recorded once; odds below the item's minimum are recorded and flagged. The scan's exposure per market is the larger of the stakes alerted (last 4 days) and the stakes placed and not yet settled. Settled results and profit are listed by `--list` and the status report (automatic results are labelled provisional, and a confirmed-only total of the results reported from the bookmaker with `settled` follows them: only that total may back a performance claim); `--reconcile` compares every `settled` reply with what automatic settlement gives from the stored statistics, reporting AGREE, DISCREPANCY (exit 1), NOT CHECKED (match not final or no stored row) or UNCONFIRMED (automatic only), and counts replies that overrode a recorded automatic result: only agreement counts towards PRD Gate 3 criterion 4; a bet still open 7 days after placing is flagged there for settling by hand (postponed match, or a player with no stored row). Closing prices are captured by `alerts/closing.py`; none has been captured yet [U].

## Local PostgreSQL

Supported: **PostgreSQL 15 or newer** (the schema needs 15 for `UNIQUE NULLS NOT DISTINCT`; CI refuses older servers). Verified: **18.6**, installed natively on this machine with the EDB Windows installer:

- service `postgresql-x64-18`, port 5432, superuser `postgres`;
- binaries in `C:\Program Files\PostgreSQL\18\bin`, which the installer does **not** add to PATH. `ci/bootstrap.sh` finds the newest version there by itself; for manual use, call `psql` by full path or add that folder to PATH. A tool that reports "no psql" has usually only checked PATH;
- the password is in `%APPDATA%\postgresql\pgpass.conf` (outside the repo; `psql` reads it automatically). Never put it in a URL, file or command in the repo;
- CI database: `prop_alpha_ci`. CI stage 6 runs `DROP SCHEMA prop_alpha CASCADE`, so `ci/bootstrap.sh` resets a database only when three checks agree: it is named exactly `prop_alpha_ci` (`CI_DATABASE_NAME`), it carries the comment `CI_DATABASE_MARKER` (set on the local one on 2026-10-05: `COMMENT ON DATABASE prop_alpha_ci IS 'prop_alpha disposable CI database'`; never set it on a database you want to keep), and its `fixtures` and `player_match_stats` are empty.

Run the full pipeline, including the database stage (from Git Bash):

```bash
PROP_ALPHA_CI_DATABASE_URL="postgresql://postgres@localhost:5432/prop_alpha_ci" bash ci/bootstrap.sh
```

Stage 6 then: drops and reinstalls the schema from `schema.sql`; runs the merge on empty staging; runs `tests/test_merge_postgres.sql` (it rolls itself back); re-applies 005 to check it is idempotent; replays the upgrade path 003 → 004 → 005; and runs the merge test again. Without `PROP_ALPHA_CI_DATABASE_URL`, stage 6 is skipped and says so.

Manual checks (PowerShell):

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -w -h localhost -U postgres -d prop_alpha_ci -X -v ON_ERROR_STOP=1 -f schema.sql
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -w -h localhost -U postgres -d prop_alpha_ci -X -v ON_ERROR_STOP=1 -f tests/test_merge_postgres.sql
```

A **fresh database gets `schema.sql` only**, because it already includes every migration. Never apply `migrations/002_staging_and_indexes.sql` to a v3.2+ schema: it reinstalls the superseded v3.0 merge function and drops the minute-logic reject predicates. Migrations are for upgrading existing databases, in numeric order.

On a machine without a native install, Docker works too (untested here): `docker run --name prop_alpha_sandbox -e POSTGRES_DB=prop_alpha_ci -e POSTGRES_PASSWORD="$PGPASSWORD" -p 5432:5432 -d postgres:18-alpine`, with `PGPASSWORD` from `openssl rand -hex 16`, then the same CI command with `postgres:${PGPASSWORD}@` in the URL.

## Conventions

- **Naming.** `snake_case` for functions, parameters and columns (`padj_tackles`, `minutes_played`). `UPPER_CASE` with `Final[...]` for module constants (`MIN_RELATIVE_VARIANCE`, `MAX_MATCH_MINUTES`). Define each constant in exactly one module and import it; never redeclare.
- **Upsert ordering.** Two different orderings apply, and they must not be confused:
  - **Lock order:** every multi-row upsert orders by its conflict key, e.g. `ORDER BY f.fixture_id, p.player_id` for `player_match_stats`, so concurrent writers take row locks in the same order and cannot deadlock.
  - **Chronological order:** `DISTINCT ON (...) ORDER BY ..., staged_at DESC` only decides which staged version wins.

  Anything else that updates `referees` must take the merge's advisory lock (`referee_job.MERGE_LOCK_KEY`).
- **Numerics.** Vectorise with numpy when operating on data arrays: exposure vectors, outcome grids, estimator inputs. Plain Python `sum` is correct, and preferred, for exact integer tallies over dataclasses (`compute_referee_coefficients`) and for short fixed-size loops (log-sum-exp over a handful of terms). Never compute a variance as \(E[X^2]-\mu^2\) in `engine.py`: use the relative form \(1/\alpha + 1/k + 1/(\alpha k)\) (AGENT.md gate G1).
- **Database changes.**
  - Put every change in a new `migrations/NNN_*.sql`. Never edit an applied migration.
  - Mirror the change in `schema.sql`.
  - Add constraints `NOT VALID`, then `VALIDATE`; build indexes `CONCURRENTLY`; set `lock_timeout`.
  - Every new `CHECK` needs a matching Python validation and a merge reject predicate.
  - Never use `TRUNCATE` on staging.
- **Secrets.** None in code, tests or scripts. Tests need no credentials. The Telegram bot token and chat id live only in the gitignored `.env` (template: `.env.example`) or the process environment; `test_no_secrets_in_repository_files` scans for token-shaped strings.
